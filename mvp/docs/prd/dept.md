# 部门管理

## 背景
系统已有用户管理（PRD-USER-001，已 reviewed）与角色管理（PRD-ROLE-001，draft）。本期新增部门管理：部门以树形结构组织（自引用父部门，最多 3 层深度），管理员可创建、查看、删除部门；用户可归属到至多一个部门（可为空）。删除部门时需显式处理其下用户与子部门。本期不做部门信息编辑（创建后名称与父部门不变更，如需调整须删除重建），亦不做跨部门批量调整。部门管理将向用户领域引入"部门归属"字段，并向角色领域引入 dept:read / dept:write 权限码（详见跨域依赖）。

## 用户故事
- 作为管理员，我希望创建部门并指定其父部门（或不指定父部门作为根），以便按组织层级维护部门树。
- 作为管理员，我希望以树形结构查看全部部门，以便直观了解组织层级关系。
- 作为管理员，我希望删除不再使用的部门，并确保其下用户与子部门得到明确处理，以避免数据残留或意外丢失。
- 作为管理员，我希望将用户归属到一个部门（或解除归属），以便按部门组织用户。

## 功能点清单
- [ ] F1：创建部门（指定父部门或作为根；校验层级 ≤3、同父名称唯一）
- [ ] F2：查看部门树（树形结构展示全部部门及其父子层级）
- [ ] F3：删除部门（有子部门则禁止删除；其下用户解除部门归属）
- [ ] F4：维护用户部门归属（分配/变更/解除/查看，一个用户仅属一个部门，可为空）

## 数据实体草图
- Department: { id, 名称(name), 父部门标识(parent_id，可空，空表示根部门), 创建时间(created_at) }。层级深度不作为存储字段，由父部门链路推导；最多 3 层。
- 用户部门归属：通过在 User 实体上增加"部门归属(department_id，可空)"字段表达（一个用户至多归属一个部门）。该字段属于用户领域（PRD-USER-001），由本 PRD 声明其引入，需 PRD-USER-001 同步更新 User 实体定义（当前 User 实体为 { id, name, email, status, created_at, updated_at }，需追加 department_id）。

## 跨域依赖
- 依赖用户管理（PRD-USER-001）：本领域要求在 User 实体上新增可空的"部门归属(department_id)"字段，以表达"一个用户归属 0 或 1 个部门"。该变更属于用户领域数据实体，需与 PRD-USER-001 协同；F4 的归属操作即建立在此字段之上。用户可在无部门状态下存在，与 PRD-USER-001 兼容（不改变用户既有字段语义，仅新增可空字段）。
- 依赖角色管理（PRD-ROLE-001）：本领域引入 dept:read（查看部门）、dept:write（创建/删除部门、维护用户归属）两个权限码。依据 PRD-ROLE-001 Q2 已决策"权限码随模块 PRD 扩展枚举"，需将 dept:read / dept:write 纳入权限码枚举；内置 admin 角色按 PRD-ROLE-001 Q4 决策自动覆盖这两个新权限码。
- 与角色管理无直接数据耦合：部门与角色各自独立，本期不建立"部门-角色"关系。

## 非功能需求
- 性能：部门树查看在常规部门数量下应即时返回并按层级组织；用户归属操作应即时完成，避免一次性全量加载。
- 安全：仅具备 dept:write 权限者可创建/删除部门及维护用户归属；仅具备 dept:read 权限者可查看部门树；"层级 ≤3"与"同父名称唯一"约束在任何入口均须生效；创建/删除/归属变更操作需留审计痕迹。
- 兼容：与现有用户管理（PRD-USER-001）兼容，不改变用户既有字段语义，仅新增可空部门归属字段；用户可在零部门状态下存在。

## 验收标准（Given/When/Then）

### F1：创建部门
- Given 管理员已登录且具备 dept:write 权限，提交合法名称与一个有效父部门 When 创建部门 Then 部门创建成功并挂在该父部门下
- Given 管理员提交合法名称且不指定父部门 When 创建部门 Then 部门作为根部门创建成功
- Given 目标父部门已处于第 3 层 When 管理员在其下创建子部门 Then 创建失败，明确提示"超过最大层级 3 层"（依据 Q4）
- Given 同一父部门下已存在名为"研发组"的部门 When 管理员在同一父部门下再次提交名称"研发组" Then 创建失败，明确提示"同级部门名称已存在"（依据 Q3）
- Given 不同父部门下已存在名为"研发组"的部门 When 管理员在另一父部门下提交名称"研发组" Then 创建成功（同父唯一允许跨父重名，依据 Q3）
- Given 管理员仅具备 dept:read 权限 When 尝试创建部门 Then 操作被拒绝

### F2：查看部门树
- Given 系统存在多层级部门 When 管理员查看部门列表 Then 以树形结构返回全部部门，正确体现父子归属与层级
- Given 系统中尚无任何部门 When 管理员查看部门列表 Then 返回空结果
- Given 管理员仅具备 dept:read 权限 When 查看部门树 Then 可正常查看，但创建/删除/归属维护入口对其不可见

### F3：删除部门
- Given 待删部门无子部门且无归属用户 When 管理员删除该部门 Then 该部门从部门树中移除
- Given 待删部门无子部门但有归属用户 When 管理员删除该部门 Then 这些用户的部门归属被置空（用户账号保留），部门被移除（依据 Q1 已决策：解除归属）
- Given 待删部门下仍有子部门 When 管理员删除该部门 Then 删除被拒绝，明确提示"请先处理子部门"（依据 Q2 已决策：禁止级联，须先清空子部门）
- Given 任一入口（含批量或快捷入口）When 对含子部门的部门发起删除 Then 均被拒绝
- Given 管理员对一个不存在的部门发起删除 When 提交 Then 操作失败，明确提示"部门不存在"

### F4：维护用户部门归属
- Given 用户 U 当前无部门 When 管理员将 U 归属到部门 D Then U 的部门归属为 D
- Given 用户 U 已归属部门 D1 When 管理员将 U 改为归属部门 D2 Then U 的部门归属变更为 D2，且仅归属 D2（一个用户仅属一个部门）
- Given 用户 U 归属部门 D When 管理员解除 U 的归属 Then U 的部门归属置空，U 账号保留
- Given 部门 D 此前被删除（其下用户已解除归属）When 查看原归属用户 Then 这些用户不再归属任何部门（依据 Q1 语义）
- Given 管理员对一个不存在的用户或部门发起归属 When 提交 Then 操作失败，明确提示"用户不存在"或"部门不存在"

## 不确定项
- [BLOCKING] Q1：删除部门时其下用户如何处理？—— 阻塞下游：F3 删除功能的验收标准（用户连带行为）与用户领域数据实体（部门归属字段的生命周期/可空语义）。已决策：解除归属——将该部门下用户的部门归属置空，用户账号保留、不删除、不迁移到父部门。理由：与 PRD-USER-001"不删除用户、保留账号"哲学一致；用户实体本就支持空部门归属（可为空）；删除部门仅解除归属、不波及用户账号，行为可预期、最小意外；避免迁移到父部门带来的隐式组织结构变更。
- [BLOCKING] Q2：删除部门时其下子部门如何处理？—— 阻塞下游：F3 删除功能的验收标准（子部门连带行为）与删除边界。已决策：禁止级联删除与自动提升——待删部门若仍有子部门，删除被拒绝，要求管理员先逐个处理子部门（删除或迁移）后再删本部门。理由：与既有领域"避免级联、显式处理"哲学一致（参照 PRD-USER-001 不做级联删除、PRD-ROLE-001 内置角色显式不可删）；杜绝意外批量数据丢失；自动提升到父部门会造成隐式组织结构变更，不可预期。
- [BLOCKING] Q3：部门名称唯一性范围？—— 阻塞下游：F1 创建校验契约与同父同级边界。已决策：同父下唯一（同一父部门的直接子部门间名称不可重复；不同父部门下允许同名）。理由：组织树中不同分支常复用部门名（如各分公司下均设"研发组"），同父唯一可消除同级歧义同时保留跨分支复用；全局唯一会过度限制常见组织建模。
- [CONFIRMED] Q4：部门树深度限制——是否 BLOCKING？如何校验？判断：非 BLOCKING（产品背景已给定"最多 3 层深度"，属已确认约束，非开放项）。已确认结论：层级上限为 3（根部门为第 1 层）。校验方式：创建或调整部门归属时，系统按目标父部门所在层级推导新部门层级（根=1，每深入一层 +1），若将超过 3 层则拒绝操作并提示"超过最大层级 3 层"。
- [OPEN] Q5：本 PRD 在 User 实体上新增"部门归属"字段，是否需要将 PRD-USER-001 由 reviewed 同步更新以纳入该字段？—— 非阻断。当前按"本 PRD 声明扩展、需 PRD-USER-001 同步更新 User 实体定义"处理；具体文档修订流程待与用户领域负责人确认，不影响本期功能与验收标准定义。
- [OPEN] Q6：部门信息（名称、父部门）创建后是否可编辑？—— 非阻断。当前按"创建后不可编辑，如需调整须删除重建"处理（与既有领域不做编辑/不可改的取向一致），后续若需部门更名或迁移可在下期迭代，不影响本期数据实体与验收标准。
