# 角色管理

## 背景
系统已有用户管理（PRD-USER-001）。本期新增角色管理模块，使管理员能定义角色（名称 + 描述 + 权限码集合）、为用户分配角色，从而以角色为载体聚合权限码，支撑后续按权限码控制操作范围。系统预置一个内置 admin 角色以保证开箱即用的兜底最高权限。本期不做角色编辑（创建后权限码不可改，需变更只能删除重建）。

## 用户故事
- 作为管理员，我希望创建角色并指定其权限码集合，以便按业务岗位聚合权限，避免逐用户逐权限地配置。
- 作为管理员，我希望查看角色列表与角色详情，以便确认现有角色配置及其权限码构成。
- 作为管理员，我希望删除不再使用的角色，以便保持角色集合整洁。
- 作为管理员，我希望为用户分配一个或多个角色（并可查看与移除已分配角色），以便用户获得对应权限码。
- 作为管理员，我希望系统内置 admin 角色且不可被删除，以便始终保留一个兜底最高权限角色。

## 功能点清单
- [ ] F1：创建角色（名称 + 描述 + 权限码集合，创建后权限码不可改）
- [ ] F2：查看角色列表与角色详情
- [ ] F3：删除角色（受内置 admin 不可删约束；删除连带处理见不确定项 Q1）
- [ ] F4：为用户分配角色（含查看与移除已分配角色，一个用户可多角色）
- [ ] F5：内置 admin 角色（预置、不可删除、持有全部权限码）

## 数据实体草图
- Role: { id, 名称(name，全局唯一), 描述(description), 权限码集合(permission_codes), 是否内置(is_builtin), 创建时间(created_at) }
- UserRole: { id, 用户标识(user_id), 角色标识(role_id), 分配时间(assigned_at) }（用户-角色关联，一个用户可对应多条）

## 非功能需求
- 性能：角色列表查看与为用户分配角色的操作，在常规角色与用户数据量下应即时返回，避免一次性全量加载。
- 安全：仅具备 role:write 权限者可创建/删除角色及分配、移除用户角色；仅具备 role:read 权限者可查看角色；"内置 admin 不可删除"约束在任何入口均须生效；角色与权限相关操作需留审计痕迹。
- 兼容：与现有用户管理（PRD-USER-001）兼容，不改变用户已有字段；用户可在零角色状态下存在。

## 验收标准（Given/When/Then）

### F1：创建角色
- Given 管理员已登录且具备 role:write 权限 When 提交一个不重复的角色名称与全部合法的权限码集合 Then 系统创建该角色并返回成功，且该角色的权限码集合按提交值固定、此后不可修改
- Given 已存在名为 "auditor" 的角色 When 管理员再次提交名称 "auditor" Then 创建失败，明确提示"角色名称已存在"
- Given 管理员提交了未知权限码 "foo:bar" When 创建角色 Then 创建失败，明确提示"权限码不合法"（依据 Q2 已决策的固定枚举）
- Given 管理员提交空权限码集合 When 创建角色 Then 角色创建成功，得到一个零权限角色（依据 Q2 已决策：权限码集合允许为空）
- Given 管理员仅具备 role:read 权限 When 尝试创建角色 Then 操作被拒绝

### F2：查看角色列表与角色详情
- Given 系统中存在若干角色（含内置 admin）When 管理员请求角色列表 Then 返回全部角色，并标识每个角色是否为内置
- Given 已存在某角色 When 管理员查看该角色详情 Then 返回其名称、描述、权限码集合及是否内置
- Given 管理员仅具备 role:read 权限 When 查看角色列表与详情 Then 可正常查看，但创建/删除/分配入口对其不可见

### F3：删除角色
- Given 存在一个非内置角色 When 管理员删除该角色 Then 该角色从角色集合中移除
- Given 内置 admin 角色 When 管理员尝试删除 Then 删除被拒绝，明确提示"内置角色不可删除"
- Given 任一操作入口（含批量或快捷入口）When 尝试删除 admin 角色 Then 均被拒绝
- Given 待删角色已被分配给若干用户 When 管理员删除该角色 Then 其连带处理（级联移除关联 / 禁止删除）依 Q1 决策而定；该条验收标准待 Q1 拍板后补齐

### F4：为用户分配角色
- Given 用户 U 存在且当前无角色 When 管理员为 U 分配角色 R1 Then U 关联 R1，U 获得 R1 的权限码集合
- Given 用户 U 已持有角色 R1 When 管理员再为 U 分配角色 R2 Then U 同时持有 R1 与 R2，其权限码为两者并集
- Given 用户 U 持有角色 R1 When 管理员移除 U 的 R1 Then U 不再关联 R1，且不再拥有 R1 的权限码
- Given 管理员对一个不存在的用户或角色发起分配 When 提交 Then 操作失败，明确提示"用户不存在"或"角色不存在"
- Given 管理员为同一用户重复分配其已持有的角色 When 提交 Then 操作无效，明确提示"该用户已持有此角色"

### F5：内置 admin 角色
- Given 系统初始化完成 When 管理员查看角色列表 Then 列表中存在 admin 角色，其权限码集合为当前全部权限码，且标记为内置
- Given 后续新增权限码进入枚举 When 查看 admin 角色 Then admin 的权限范围自动覆盖新权限码（依据 Q4 已决策）
- Given 任何操作入口 When 尝试删除 admin 角色 Then 均被拒绝

## 不确定项
- [BLOCKING] Q1：角色删除时，已分配该角色的用户如何处理？（方案 A：级联移除这些用户的 UserRole 关联，用户保留、仅失去对应权限码；方案 B：若有用户仍在使用该角色则禁止删除，要求先逐个解除全部分配）—— 阻塞下游：F3 删除功能的验收标准（删除连带行为）与 UserRole 实体生命周期边界、用户权限回收语义。当前未决策，待产品负责人在 A/B 间拍板；F3 中"连带处理"验收条已显式留空待补。
- [CONFIRMED] Q2：权限码采用固定枚举。已决策：当前权限码限定为 {user:read, user:write, role:read, role:write} 四个，创建角色时对权限码逐项校验，未知码拒绝；后续新增模块时随对应 PRD 扩展该枚举。理由：保障创建表单可固化为可勾选项、避免拼写错误与无效码污染契约，同时通过"随模块 PRD 扩展"保留演进能力，未额外新增功能。另决策：权限码集合允许为空（允许创建零权限角色作为占位），不影响契约。
- [CONFIRMED] Q3：角色名称全局唯一。已决策：名称在全部角色中不可重复（含与内置 admin 冲突）。理由：角色以名称为业务标识，重复将导致分配与展示歧义；属隐含完整性约束，未新增功能。
- [CONFIRMED] Q4：内置 admin 角色的权限范围。已决策：admin 持有当前全部权限码（即 Q2 枚举的全部项），随枚举扩展自动覆盖新码。理由：admin 为兜底最高权限角色，须始终覆盖全部可操作范围；产品已隐含（"系统内置一个 admin 角色"）。
- [OPEN] Q5：单个用户最多可持有几个角色？—— 非阻断。当前按"无硬性上限"实现，后续可根据运营数据在界面层加超额提示。不影响数据实体（UserRole 表达用户与角色的关联）与本期验收标准定义，可后续迭代。
