## 2 · 本轮新发现的问题

### P1 · 规则声明与实现漂移（Reviewer 发现）
**现象**：SEC-003b 规则文档声称"check-rules.mjs 扫描 throw new AppError"，但脚本未实现该分支。Reviewer 抓出此"声明 vs 实现漂移"。

**根因**：写规则文档时为满足 META-001 关键词要求，倾向声称有机器校验，但实现没跟上。META-001 只检查"校验方式段含关键词"，不验证"声称的脚本分支真存在"。

**反推优化**：META-001 升级为 META-003——"校验方式段声称的脚本/命令必须真实可执行"。可用静态分析：提取校验方式段里的 `check-rules.mjs` 关键词，与脚本内实际注释分段（如 `// === SEC-003b ===`）比对，声称无对应实现即报漂移。本轮临时处理：把 SEC-003b 措辞改为诚实表述（人工 Review + 契约测，不声称脚本扫描）。

### P1 · 反向缺口：脚本 enforce 但无规则文档
**现象**：CODE-001/002/003 早期由 check-rules.mjs enforce，但因 forbidden-patterns.md 被删（拆分时遗漏），曾出现"脚本在查但无规则文档定义"的反向缺口。本轮已补回 forbidden-patterns.md。

**根因**：规则文档与脚本是两份独立资产，无双向绑定。删文档不删脚本、加脚本不加文档都会漂移。

**反推优化**：META-004——"check-rules.mjs 的每个 enforcement 分支必须对应一条 .trae/rules 规则 ID"。脚本启动时自检：扫描自身 `// === XXX-NNN ===` 注释，与 .trae/rules 的规则 ID 双向比对，缺任一方向报错。本轮通过补 forbidden-patterns.md + 脚本注释对齐临时解决。

### P2 · BLOCKING 项仍需人工拍板
**现象**：BA 正确标了 BLOCKING，但"谁来拍板"在工作流里是空白——本轮由编排者（我）替产品负责人决策。真实场景需明确"BLOCKING 项的决策责任人与 SLA"。

**反推优化**：工作流定义"BLOCKING 项的决策权属产品负责人，SLA = 1 工作日；超时则该 PRD 降级为 backlog"。Skill 提示词：BA 标 BLOCKING 时同时生成"决策请求"（含 A/B 方案建议），推送产品负责人。

## 4 · 结论

第二轮验证了第一轮所有反推优化项**全部真正生效**：
- P0 规则机器化 → 100%，新代码零 blocker（CODE-004 在生成时即被遵守）
- 测试先行拆分 → 73 用例一次全绿，impl-writer 零改测试
- BLOCKING 标记 → G1 精准拦下，不再漏到下游
- advisory 区分 → Tech Lead 与 impl-writer 协作无歧义

但演练也证明：**规则体系本身会漂移**。META-001 解决了"无校验不立规"，但暴露了"声称有校验但实现缺失"与"脚本有但文档缺"的双向漂移。下一轮第三优先级：META-003/004 双向绑定校验，让规则文档与脚本成为同一事实源的两个投影。

> 规则机器化不是一次性工程，而是需要"元规则"持续守护的活系统。
